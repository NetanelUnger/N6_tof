# התאוששות אחרי חריגת האבחון A23

המצב הנוכחי חסום. A23 נכתבה דרך USB, עלתה ואושרה, ועברה100 פריימי NPU.
לאחר מכן נעצרה ב־HardFault בזמן OTA ל־B24. אין הוכחת ריצה חיה מאז החריגה.
B24 לא הושלמה ולא אושרה; היא החליפה את B22 בחריץ B. **אין להציג את B22
כתמונת fallback שנותרה בלוח.** B25 בנויה וחתומה בלבד, טרם הותקנה.

כל החיבורים, השולח והבעלות נסגרו; אין הקלטה מוכנה. לא בוצעו איפוס,
חיבור debugger או כתיבה נוספת לאחר החריגה. המשתמש התבקש להודיע ״מוכן״
לפני פעולה פיזית. אין להתחיל הקלטה או חומרה עד אישור מוכנות חדש.

## מה נשמר ומה הוכח

| פריט | מצב |
|---|---|
| A23 | תמונה חתומה, אישור אתחול נלכד לפני הכשל; אינה גרסה תקינה לשימוש כעת בגלל מסלול האבחון |
| B24 | חלקית; בלוקים1–139 קיבלו ACK, כ־142080 בתי image, ללא EOT/finalization |
| metadata לאחר החריגה | לא נקרא עצמאית; האישור האחרון שנלכד הוא A23 |
| FSBL/Secure | לא נכתבו בניסויים אלה; שרשרת האתחול הקבועה נשמרה |
| B25 | תיקון עיצוב לוג נדחה ל־Radio; אימות חתימה במחשב עבר; חומרה ממתינה |
| תמונת RAM המקורית | `.local-dependencies/recovery-20261022/candidate.elf`, SHA256 ‏`6a6a5d1fcd70be9ed1826624b4e3bf97d5ec35758c9f1915772e1fa4b5c8d781` |
| גיבוי NOR ראשון4MiB | `resume-20261022/nor-first.bin`, SHA256 ‏`cb3d9e4ffee29d832c7ca0cb516f06232dba2c4c5598e77fd6c81ce7feb9f05a` |
| גיבוי4MiB אחרי שרשרת האתחול | `inspection-after-bootchain-program/nor-first.bin`, SHA256 ‏`6cc2cfb51d893b06e75d32c1614818406bcc2a6219f68cb2b98a9c9cae43faaf` |
| B11 המקורית לשחזור במחשב | `resume-20261022/recovery-B-trusted.bin`, SHA256 ‏`9c8b0516281fe19bc684700f7922a7437afa22b14be00e2f9e2559a70a8386d4` |

שלושת נתיבי הגיבוי האחרונים יחסיים ל־`.local-dependencies/xip/`.
ה־hashים נבדקו שוב אחרי הכשל. גיבוי NOR היסטורי אינו צילום של מצב NOR
הנוכחי, ואין לשחזר את כל4MiB אוטומטית או למחוק אזורים לא קשורים.

## סדר ההתאוששות הבטוח

1. אחרי הודעת מוכנות חדשה: להכין בעלות וקלט UART פסיבי מוקשח ב־COM6,
   ‏DTR/RTS כבויים, זהות ST-LINK מדויקת ו־heartbeat. לא לבקש פעולה פיזית
   לפני שההקלטה פתוחה ואורך החיים שלה מאומת.
2. לתאם ניתוק כל מקורות המתח, שינוי ל־DEV: ‏BOOT0=1–2, ‏BOOT1=2–3,
   וחיבור מחדש. המטרה היא ROM מבוקר, ולא להפעיל שוב אוטומטית את A23.
3. לבדוק זיהוי ST-LINK/AP1 ומצב DEV בפועל. לא להסיק אותו מהג׳מפרים בלבד.
   להשתמש תחילה ב־`Tools/read_xip_recovery.py` עם ELF/hash שנבדקו ובעלות
   מתאימה. הכלי עוצר ב־FSBL שב־RAM לפני בחירת אפליקציה, אינו מאפס ואינו
   כותב NOR. אין להפעיל במקביל debugger או קורא UART אחר.
   preflight במחשב עבר ל־`v25-B-rx-resume-deferred/FSBL.elf`, SHA256
   `de7f3c84c656527b8fe594704982fa84e22d4b0f6e5c8a8fbf6b0e30d3d644f7`:
   branch/hash וארבעת סמלי העצירה אומתו; שום חיבור לחומרה לא נפתח.
4. לשמור קריאה חדשה כפולה ועקבית של אזורי recovery/metadata, ולאמת
   A23 ואת היעדר תמונה שלמה ב־B. אם המצב שונה — לבדוק לפני כל ניסיון.
5. להחזיר שליטה תחילה דרך מסלול RAM שמור ומוגן. לשמור Cloud/תמונות כבויים,
   `settings writes=0` ו־NCP preserve. ה־ELF המקורי לעיל הוא גיבוי מדויק;
   אין להחליפו סתם ב־`Debug` רגיל או להריץ `Debug-NonSecureRam.ps1 -NoBuild`
   בלי לבדוק את שלושת ה־ELF, סמלי העצירה והתאמת Secure/NSC קודם.
6. לפני תיקון B: לאמת את Secure RAM המסוים שיתמוך בחבילת XIP ובשערי NSC
   הקיימים, ואת קורא/כותב ה־USB האמיתי. חבילת B25 מיועדת לחריץ B ואינה
   דורשת שינוי FSBL/Secure קבוע, OTP או הרשאות. גרסאות ישנות כגון B22
   אינן חבילת downgrade רגילה מעל metadata מאושרת23.
7. רק לאחר הוכחת שליטה/metadata: התקנה אחת דרך ה־installer החתום הקיים
   ל־B25, שמירת A, ואימות hash/signature. לא לשחזר image שלם אוטומטית
   בעקבות timeout או אי־ודאות. אין לשנות שרת ייצור.
8. לתאם FLASH boot עם הקלטה מוכנה, להוכיח אישור גרסה/PC בפלאש, לבדוק
   stack margin בזמן אמת, HIL100, USB/OTA, ‏SUSP→resume אמיתי ושחזור כשל.
   בדיקות המחשב אינן תחליף לשלבים האלה.

אחרי reset יש גם לבדוק שפקודות binary ישנות מה־OTA שנכשל לא חוסמות את
ראש התור בענן. ה־firmware דוחה binary שאינו שייך ל־command פעיל; לא מניחים
שפקודות ישנות נעלמו. אין לקרוא/לייצא tokens או לשנות credentials לצורך זה.

## הסיבה לתיקון המחסנית ומה עוד חסר

ב־A23 הוכנסה קריאת `Debug_UART_Log` ממסלול SPI worker של768 בתים.
מדידת שרשרת מה־ELF: מעטפת8 + worker24 + engine88 + logger296 + snprintf136
+ formatter144 + integer formatter48 + common32 = **776 בתים לפחות**, לפני
פסיקות/FP. מסגרת service בת8 בתים נשלפת לפני tail-call, ולכן לא נספרה פעמיים.
זהו מסלול סטטי שחורג מהקיבולת ומתאים ל־STKOF שנלכד; PC מדויק לא נקרא
כי מסגרת החריגה לא הייתה תקינה.

ב־B25 רק מונה מתעדכן ב־SPI; הדיווח עובר ל־Radio בעלת8192 בתים. שרשרת
החידוש המקומית היא128 בתים, אך זו אינה הוכחת שיא המחסנית הכוללת. אין
להוסיף עיצוב, `printf` או buffer מקומי גדול ב־SPI/ISR. אין להגדיל מחסנית
סתם כדי להסתיר מסלול שגוי. יש למדוד high-water ולבדוק גם ספריות/מסגרות
פסיקה, וכן נתיבי abort/error, לפני קבלה.

חבילת B25: ‏500096 בתים, SHA256
`034173f3191f53bb1a70ea439a0715ef1d8c2ca933712e4f558f4055a716af1e`.
heap capacity בבנייה: RAM369104, ‏XIP ניסיוני861944; אלה גבולות linker,
לא זיכרון פנוי בזמן אמת. הקוד הניסיוני אינו ברירת המחדל וטרם התקבל בחומרה.

פירוט המדידות, הכשלים וה־SDK side effect הלא־ודאי נמצא
ב־[תוצאות החקירה](xip-spi-ovr-experiments-20261023.json).
